# tracking-core

An independently written deterministic baseline for six body IMUs plus a live HMD, with optional feet and upper arms. It consumes **right-handed standing-space**, meters, +Y up, -Z forward, XYZW quaternions. The protocol adapter owns coordinate conversion. It does not receive SteamVR raw-space transforms.

`TrackingCore::new(TrackingConfig)` validates dimensions and thresholds. Assign stable sensor identities with `set_assignments`, call `ingest` for each sample, and call `solve` each frame with fresh HMD/controller anchors. Times must use one monotonic seconds origin. Samples are never reordered by arrival list position, and old packets are rejected. Evidence stamped more than 2 s ahead of the newest time the core has seen (latest `solve` time or accepted evidence) is rejected without changing any state, so one bad clock cannot make later packets "out of order". The cache holds 256 identities; when full, the least recently seen unassigned identity is evicted. `forget_sensor(id)` drops one identity's evidence (an assigned role then stays invalid until new measurements arrive).

The HMD reports the eye point, not the head pivot. The neck is placed at `R_head * (0, -head_to_neck_m, +eye_forward_m)` from it (default 8 cm behind the eyes, valid 0–0.20 m; older profiles load the default), so pitching or turning the head about the neck does not move the inferred body. The default dimensions are consistent: `Anthropometrics::standing_chain_height_m()` (head-to-neck through ankle-to-sole) equals the default 1.65 m eye height, so neutral soles touch the floor. `Anthropometrics::normalize_chain_height()` makes an inconsistent profile consistent by adjusting `chest_to_hip_m` only (left unchanged with an error when that would leave its valid range); the app applies it on profile load and whenever the eye height is set. A successful live neutral reports `CalibrationStatus.floor_mismatch_m` = averaged HMD height over the stable window minus that chain height (positive: feet would float). It is a diagnostic only; calibration is not rejected on it, and it is `None` in preview.

`rebase_standing_space(yaw)` must be called when the standing space itself was rotated about +Y (for example a recenter): after it, outputs equal the previous ones rotated by `R_y(yaw)` about the origin. It rotates the reference heading, every role's heading alignment and the stored neutral heading by the same angle, clears head/knee history, the preview-motion origin, target velocities and the HMD discontinuity baseline (so the same event cannot be detected again), and keeps mounting, dynamic yaw, stance-filter corrections, calibration flags and recovery undo. It also drops contact hypotheses, leg-IK anchors and the stance filter's motion history (the same happens on a detected discontinuity that cannot be rebased). Nonfinite input is ignored. Applications normally do not call it for SteamVR events any more (see below); it remains for explicit rotations and older recordings.

**SteamVR tracking-space events (synthetic validation only).** The calibration lives in the standing space, so the only thing that matters to it is whether the headset's *standing-space* pose stayed physically continuous. `note_tracking_space_event(at, transform_yaw)` tells the core that something may have moved the space (a new anchor-helper session, or a material raw-to-standing transform change, with that change's yaw when it is a pure yaw). It is a hint, never evidence and never a clear. The discontinuity detector then decides with the pure `tracking_space::decide`, comparing the previous and the new usable headset sample (`dt` apart):

- `dt` > 2 s: `Resumed`. With a live calibration the calibration is kept (same headset, same room: assumed the same standing frame), headset positions before the gap are not compared with later ones (head history, neck reference and a running movement session are dropped), and with the stance filter enabled its heading uncertainty is widened by 15° (legs) and 8° (chest/hip) 1σ in quadrature so it can re-converge quickly if that assumption was wrong. `EstimatorStatus.headset_resumptions` and `last_headset_gap_secs` report it.
- `dt` < 0.1 s always, and up to 2 s when a hint applies (the hint covers comparisons whose previous sample is at most 0.5 s newer than the hint): the change is compared with plausible head motion, `tracking_space::plausible_motion(dt)` = 0.25 m + 4 m/s and 25° + 10 rad/s over the first 0.1 s (the previous consecutive-sample thresholds), then 1.5 m/s and 60°/s (0.65 m / 82° at 0.1 s, 2.0 m / 136° at 1 s, 3.5 m / 196° at 2 s). A jump rebases by the transform's exact yaw when the observed headset yaw change agrees with it within `agreement_tolerance(dt)` = 10° + 20°/s·dt, otherwise by the observed yaw change; without usable horizontal facing (above 0.3) only histories and velocities are reset. Without a jump nothing changes, unless the observed yaw change is clearly the transform's (within tolerance of it, outside tolerance of zero and closer to it than to zero), which recognises a slow recenter across a gap. `EstimatorStatus.last_rebase_evidence` says which (`transform` or `observed_jump`).
- Otherwise (a gap without a hint): not compared.

A desktop (preview) calibration never follows the headset space. Rebases need `enable_auto_rebase`; the long-gap handling does not.

`align_preview_to_headset(now, anchors)` carries a complete desktop calibration over to live use without repeating it. It returns an error and changes nothing until the user is upright and still: the neutral gate's stability checks (stable core sensors, segment tilt within the neutral limit, a dense, still, upright headset history over the stable window; the configured eye height is **not** enforced because changing it would void the calibration) and every core segment within `recovery_max_yaw_degrees` (20°) of the torso heading. Then it rotates the reference heading, every heading alignment, the neutral heading and manual-mount headings by `headset yaw − torso heading` (circular mean of chest and hip yaw), the same left-factor rotation as `rebase_standing_space` with mounting untouched, clears the preview flag, resets the estimator layers, widens the stance filter's uncertainty (legs 10°, chest/hip 6°), resets recovery and its undo, and records the floor mismatch. Like a live neutral capture it assumes the head faces the same way as the torso. `tests/tracking_space.rs` checks that afterwards every target equals what a live neutral plus skiing-pose calibration in the same pose produces, within 1 mm and 0.1°.

`stable_headset_height(now)` is the mean headset height over the stable window when that window passes the neutral gate's headset stability check. `calibrate_neutral_with_config(now, anchors, preview, config)` adopts a new configuration (for example an eye height measured from the headset, with dimensions rescaled) only after the neutral gate passes under it, then captures; a rejected capture leaves configuration and calibration untouched.

`TrackingConfig.estimator` (`EstimatorConfig`, older configurations load with every feature off, which is also the core default) adds stance-anchored estimator section 5 behaviour. **All of it is verified by synthetic tests only** (`tests/estimator.rs`), not by live or comparative measurements:

- `enable_prediction`: each sensor keeps a `prediction::AngularRateEstimator` fed only by accepted measured quaternions (never held tokens; reset on health errors, transport revocations and profile restore). Output segments with a fresh measurement are extrapolated to `now + prediction_lead_secs` (0–30 ms, total horizon capped by the rate config). Held, stale or silent (> 60 ms by default) sensors are not extrapolated. Calibration, stability gates and recovery always use the raw latest samples and history.
- `TargetPose.angular_velocity` is the owning segment's measured rate rotated into standing space (chest, hip, thighs for knees, foot IMU or calf for feet, upper arms for elbows); `linear_velocity` is a smoothed finite difference of the published position. Both are zero for invalid targets and non-live frames, whether or not prediction is enabled.
- `enable_hmd_extrapolation`: HMD and hand positions are advanced by their reported `AnchorPose.linear_velocity` (finite, under 10 m/s) over their age, at most 30 ms. Orientation is not extrapolated; calibration gates and head history use the raw anchor.
- `enable_auto_rebase`: with a live (non-preview) calibration, consecutive usable HMD samples less than 0.1 s apart that move more than `0.25 m + 4 m/s·dt` or turn more than `25° + 10 rad/s·dt` are treated as a recenter or tracking jump, and after `note_tracking_space_event` samples up to 2 s apart are compared with the time-scaled thresholds above. When both head forward vectors have a horizontal length above 0.3, the standing space is rebased by the yaw change (or the agreeing transform yaw); otherwise (for example looking straight down) only histories and velocities are reset.
- `enable_stance_heading` and `enable_leg_ik` (core default off, app default on) integrate the stance-anchored estimator layers of [the specification](../../docs/research/stance-anchored-estimator.md). **They are validated on synthetic data generated with the estimator's own kinematic model only** (`tests/integration_estimator.rs`, plus the standalone module tests); nothing here is a measured accuracy result on a worn body. See the section below.
- `TrackingFrame.estimator` reports whether prediction was active, the HMD extrapolation time, rebase count and last angle, detected discontinuities, and the stance layers' state (below). `acceleration_mps2` means **gravity-removed linear acceleration**; pass `None` when the firmware convention is unknown. Actual quaternion packets use `SensorProvenance::Measured`, which is also the backward-compatible deserialization default for older captures.

Call `calibrate_neutral(now, anchors, false)` only after instructing the user to stand straight with arms down and head facing forward with the torso. At least 650 ms of stable sensor and HMD history is required by default; the explicitly marked firmware-held compatibility case below can supply an assumed unchanged interval in place of new sensor packets. Call `solve` during that period to record anchor history. Initial arbitrary sensor mounting cannot independently establish whether a limb is anatomically straight: this remains a user assertion. Later attempts reject incompatible calibrated segment tilt. `preview=true` allows an artificial standing anchor but marks every body target invalid for live output until a real session calibration succeeds.

Neutral alone produces a provisional pose. Then call `calibrate_forward(now)` while the user holds the instructed skiing pose facing the same direction. It separates each sensor's independent world-yaw alignment (left factor) from its physical mount (right factor). All six roles must supply sufficient, stable and direction-consistent motion, and commit atomically. `direction_calibrated()` and `CalibrationStatus.direction_calibrated` distinguish completed direction calibration. Live targets, recovery and knee correction require it. The separate initial `heading_alignment` is not included in `SegmentPose.yaw_correction_degrees`, which reports the later dynamic correction (recovery, legacy knee correction) plus the stance-filter correction applied to that frame. [Functional mounting math and limitations](../../docs/research/functional-mounting.md).

**Movement calibration (experimental, synthetic validation only; the app's primary method).** Instead of the held skiing pose, `begin_motion_calibration(now)` starts a `motion_calibration::MotionCalibrator` from the stored neutral capture, with the same preconditions as `calibrate_forward` (a neutral for the current assignments, at most 300 s old, not followed by a heading recovery; `motion_calibration_available(now)` checks them without side effects). While the session is active, every accepted **measured** sample of a core-assigned sensor is forwarded (firmware-held tokens and optional roles never are), and in live mode every new usable HMD sample is forwarded so the neck pivot's displacement during a bow can supply body-forward. The live neck pivot at neutral is computed from the HMD pose averaged over the neutral stable window; desktop preview has none. `motion_calibration_status()` evaluates progress, per-segment blockers and warnings; `TrackingFrame.motion_calibration` carries the same status refreshed at most every 0.1 s (`None` without a session; older recordings load with `None`). `finish_motion_calibration(now)` solves atomically and commits exactly like `calibrate_forward` (mounting, heading alignment, dynamic yaw zeroed, functional roles, direction readiness, estimator-layer resets), using the module's selected reference: the headset-fused heading when available and not flagged, else the neutral headset yaw. The published reference heading follows that reference. With the stance heading filter enabled its heading uncertainty is then widened (legs 10°, chest/hip 6° 1σ, combined in quadrature) because toe-out or knees-out squats bias leg headings by 5–16° in synthetic tests and only the headset-referenced filter can remove that. On error nothing changes and the session continues. `cancel_motion_calibration()` discards it; `clear_calibration`, `restore_profile`, an assignment change, anthropometrics changes, a new neutral capture and a standing-space rebase or HMD tracking jump end it (a rebase or jump also drops the stored neck reference, so a later session uses yaw only). Limits are in [motion-calibration.md](../../docs/research/motion-calibration.md); `tests/motion_calibration_core.rs` exercises the integration.

Stock SlimeVR firmware 0.7.2, and DIY/development builds reporting names such as `main` or `git-<rev>`, can suppress unchanged quaternion packets indefinitely. The transport, which sees the handshake, status and sequence continuity, vouches for the build; the core requires only a non-empty firmware name of at most 64 bytes. The transport can submit `SensorProvenance::FirmwareHeld` only under the named compatibility assumption: a previously received quaternion, a named firmware build, healthy reported sensor state, continuous packet-sequence epoch and transport evidence younger than 1.5 seconds. The original `received_at_secs` and quaternion must match the actual stored observation. `observed_at_secs` timestamps the assumption check; it does not timestamp a new orientation measurement. Held tokens never enter measured history, refresh measured acceleration, or increase the measurement count.

Held orientations have confidence at most 0.45 and explicit `FirmwareHeldOrientation` evidence. `SegmentPose` exposes the original measurement time/age and `uses_firmware_hold`; calibration records `used_firmware_hold` when continuity assumptions supplied its stability evidence. The check still examines actual orientation changes during the window, and repeated held tokens cannot conceal measured motion. Experimental knee correction skips held inputs. A packet gap, reordered evidence, an empty or overlong firmware name, changed held quaternion, failed health report or expired evidence lease revokes holding until a new real rotation arrives. `revoke_firmware_hold` records a continuity loss; `mark_sensor_unhealthy` additionally invalidates even a recently measured pose immediately. The runtime must separately invalidate session calibration on reboot/rejoin and must not pass measurements while sensor status is non-OK.

This policy is a firmware compatibility assumption, not proof that a sensor is currently measuring the same pose. Heartbeats cannot reveal a final lost movement packet until a later sequence number exposes the gap, and an acknowledged status is not a continuous health measurement. Unnamed firmware and ordinary stale measurements receive no freshness extension. The source basis and observational limits are documented in [tracker-stream-observability.md](../../docs/research/tracker-stream-observability.md).

Profiles serialize stable assignments, dimensions and mounting transformations. Schema 2 records certified role identities; schema 1 remains readable but cannot establish direction readiness. Restoring a profile requires fresh neutral and forward calibration (or explicit manual setup/confirmation) because strap placement and sensor heading origins may change. The first neutral after restoration is provisional and does not silently reuse saved direction certification. Ordinary neutral repeats within a valid session preserve certified physical mounts and recompute session heading. Manual bend-direction edits preserve neutral through paired transforms and change the heading alignment by the forward delta only; dynamic yaw (recovery, knee correction) is a separate left factor that the edit neither absorbs nor resets. Physical XYZ trims intentionally change alignment and require explicit confirmation. Manual undo/reset restore mount and alignment and keep yaw accrued since the edit. Confirming a never-certified, unedited role zeroes its yaw so no unchecked offset becomes active. Manual controls and undo are session-local; redo manual mounting after a restart or full clear.

`request_recovery(now)` is an explicit user assertion of the instructed standing, forward-facing pose. A gesture detector must be opt-in to that instruction. The request waits for its impulse to settle and requires fresh, continuous stable data for the six core roles, valid HMD, compatible height/tilt and at most 20 degrees of heading disagreement by default. Direction-certified optional roles are updated only when their own evidence is fresh and passes the same checks; a stale or unstable optional role neither blocks recovery nor receives a new yaw, and uncertified roles are never touched. Recovery changes yaw offsets only and keeps the neutral capture for manual edits, but forward calibration requires a new neutral afterwards. Its one-step undo subtracts exactly the per-role deltas it applied, so later corrections survive. Small head-only turns and common-mode body yaw drift are observationally ambiguous; an incorrect user assertion can cause a bounded wrong yaw reset. Ordinary tracking never rotates the body to match head heading.

### Stance-anchored estimator layers (synthetic validation only)

Every frame the published skeleton (neck, chest, hip, hip joints, knees, ankles) comes from one function, `chain::solve_chain`, which the stance filter also linearises, so the filter's model and the published skeleton cannot diverge. With both new flags off the output equals the previous inline kinematics to float noise.

The layers run only for a live session (usable HMD, completed direction calibration, no desktop preview) with at least one foot whose whole chain (chest, hip, thigh, calf) is valid (contacts and leg IK accept firmware-held segments; the filter uses freshly measured ones only). Otherwise contacts and leg IK are reset and the filter keeps its corrections but forgets its motion history. Per frame: segments (with corrections and optional prediction) → `solve_chain` → `leg_ik::SupportFloor` (leg IK on; a vertical translation of pelvis and legs) → `ContactTracker` on the floor-corrected ankles (speed gates widened by the filter's yaw uncertainty times the smoothed horizontal headset speed, `contact_speed_allowance_mps`, plus a torso-motion allowance in double support, `contact_torso_allowance_mps`) → `StanceHeadingFilter::step` on the uncorrected chain (horizontal displacement only, which the floor correction does not change; its release requests release contacts) → `LegIkSolver::solve` on the floor-corrected positions (its lock-break requests release contacts) → publish.

- **Stance heading filter.** Owns a per-`Role::CORE` yaw correction applied as an extra left world yaw: total yaw = heading alignment + dynamic yaw + stance correction, in every path that builds a segment rotation (output, prediction, calibration gates, recovery). A correction computed in a frame takes effect from the next frame, so the published chain is exactly what the filter saw. Recovery computes its delta from the fully corrected rotation and stores it in the dynamic yaw only; the stance correction is kept (its covariance returns to the initial value), so the published heading equals the HMD heading right after recovery and `undo_recovery` restores it exactly. Neutral/forward calibration, `clear_calibration`, `restore_profile`, core assignment changes, body-dimension changes, switching the flag off and manual mount edit/undo/reset/confirm of a core role zero the corrections. A revoked firmware hold or a sensor error widens that segment's heading uncertainty (10°, once per outage).
  Since the first live session (2026-11-15) the filter estimates **leg yaw only** by default (`stance.estimate_torso_yaw = false`): chest and hip yaw are held by the deadbanded priors, chest/hip lever changes enter the noise budget with `torso_motion_noise_ratio` 0.5 (legs 0.10), increments whose torso lever change exceeds their leg excitation (`max_torso_excitation_ratio` 1.0) are not used, and accumulated corrections are bounded (`max_leg_correction_degrees` 30, `max_torso_correction_degrees` 12; `stance.correction_limited` reports a bound that holds).
- **Leg IK.** When on, the published chest, hip, hip-joint, knee, ankle and toe joints and the Chest/Waist/Knee/Foot target positions come from the IK output, and a foot without a direction-certified foot IMU gets the IK's flat-foot orientation (its published angular velocity is the calf rate scaled by the remaining rigid weight). Measured segment orientations are never changed, and validity and confidence never depend on IK: it cannot make an invalid target valid.
  The two-bone solve (changed 2026-11-16; synthetic regressions only, worn validation pending):
  - *No margin at full extension.* `reach_margin_m` (1 mm) protects the minimum reach only. The previous maximum reach of `thigh + calf − 1 mm` bent every locked straight leg: a leg shortened by `d` from straight moves its knee sideways by about `√(thigh·d)`, so 1 mm of forced shortening is roughly 2 cm of knee offset.
  - *Soft full extension.* Near full extension the shortening `d` is replaced by the cubic deadband `d³/(d² + s²)` with `s` = 5 mm (`FULL_EXTENSION_SOFT_M`), pinned to the measured leg: a target at the FK hip–ankle distance reproduces the FK reach exactly, sub-millimetre noise on a locked straight leg moves the knee by well under a millimetre, and a real bend converges to the plain solution. An earlier square-root softening over 3 mm was replaced because synthetic verification measured standing-still knee jitter roughly doubling against the committed code, whose 1 mm margin had acted as an accidental deadband.
  - *Measured-flexion guard* (`knee_flex_slack_rad`, 1°). The lock is a hypothesis; the thigh and calf orientations are measurements. The guarded reach keeps the knee's interior angle within the slack of the angle the two sensors measure; the rest of the request slides the ankle along the hip–anchor line, so the published ankle can stop short of or pass its anchor while `foot_locked` stays true. The applied reach is a linear blend `free + (guarded − free) × (1 − standing-floor weight)`: an upright standing leg is unguarded as before, a leg without the prior is fully guarded. The reach is blended rather than the slack angle widened, because a few degrees of slack already free centimetres of reach and a widened angle acted like a switch near the end of the thigh taper. Reason for the guard: with the `√(thigh·d)` relation a straight leg compressed by 4 mm raises its knee by about 4 cm, so for a lying or long-sitting wearer any headset motion toward the locked feet lifted the legs. The default 1° caps the knee rise of a straight 0.45 m thigh at about 4 mm.
  - `reach_margin_m` is capped inside the solve at a quarter of the reach range, so an absurd configured value cannot straighten a bent leg.
  - *Floor bound on the guarded ankle.* The guard moves the ankle along the hip-to-anchor line; with `floor_clamp_enabled` the reach is shortened so the ankle is never below `ankle_to_sole_m − floor_margin_m` (or the target, if that is lower). The floor outranks the measured knee angle.
  None of this measures or corrects absolute pelvis position. [Investigation and sources](../../docs/research/seated-ik-investigation.md).
- **Standing-floor prior** (`upright_leg_weight`). A per-leg weight in 0..1: `max(thigh taper, bowed) × calf taper`. The calf taper is `flat_full_tilt_rad` 40° → `flat_zero_tilt_rad` 60° from vertical and the thigh taper `support_thigh_full_tilt_rad` 60° → `support_thigh_zero_tilt_rad` 80° (both `1 − smoothstep`); `bowed` rises by smoothstep from 0 to 1 as the forward lean of the mid-spine goes from `squat_bow_start_tilt_rad` 20° to `squat_bow_full_tilt_rad` 35° (forward lean only; sideways and backward leans count as zero). An invalid thigh or calf rotation gives 0. Setting both thigh thresholds at or above π ablates the thigh taper, and both squat-bow thresholds above π/2 ablates the bow term (`validate` rejects an inverted pair). The weight scales the support-floor pull-down, the planted-anchor floor attraction and the measured-flexion guard above. It is a heuristic, not a contact classifier. A chair and a parallel squat fold the legs alike; a squat balances the torso forward over the feet, so a folded leg under a forward-bowed torso keeps the prior, while an upright or reclined seated wearer loses it. Known costs: a wearer leaning well forward on a seat with the feet off the floor gets the pull-down back, and a perched pose (thigh about 60–70°) with a forward lean and the feet on a rung is still pulled down. The weight does not change contact eligibility, horizontal foot locks, below-floor raising or measured segment rotations.
- **Support-foot floor constraint** (`leg_ik.support_floor_enabled`, raise part `floor_clamp_enabled`). The lowest usable FK ankle is the support foot. Above the floor it lowers the pelvis and both legs rigidly (chest by the spine fraction, neck and head never) toward `ankle_to_sole_m`. The pull is `min(gap, budget, pelvis room above support_floor_min_hip_height_m (0.15 m)) × standing-floor weight × explained`, low-passed with `support_floor_tau_secs` (60 ms):
  - `budget = support_floor_base_m` (2 cm) + `support_floor_tilt_gain` (1.0) × `TorsoFlexion::bow_vertical_m`. That is `neck_to_chest·(1 − cos θ_chest) + chest_to_hip·(1 − cos θ_spine)` with each segment's term weighted by its lean direction: full for a forward or sideways tilt, fading linearly to none for a straight backward lean (the segment's own forward axis against gravity, so heading drift does not enter). A torso reclined against a backrest or lying supine is supported, not bowed, and earns only the base budget.
  - `explained = 1 − smoothstep(budget, 2·budget + 5 cm, gap)`. A gap the budget covers is closed in full; a gap well beyond it contradicts "this foot is on the floor" (a jump, a step or box, a stool, a bed), so the pull fades to zero instead of spending the whole budget. With an upright torso a foot more than 9 cm up is not pulled at all.
  Below the floor (by more than `floor_margin_m`) the body is raised at once by the full amount, independently of the prior, the budget and the fade; the old ankle-only clamp that bent the knees is gone. `torso_slack_gain` (0.3) adds `0.3 × TorsoFlexion::bow_horizontal_m` to the root-correction limit, the lock-break radius and the horizontal anchor-creep deadzone. That is `neck_to_chest·sin θ_chest + chest_to_hip·sin θ_spine` with the same lean-direction weights as the budget: a forward or sideways bow keeps the widened limits, a backward lean or supine torso earns none, so a lying wearer's slowly moved leg is not held to a stale anchor. A planted anchor's height target is the floor ankle height for an upright leg whose FK ankle is within `planted_floor_full_m` (3 cm) of it and the FK height beyond `planted_floor_zero_m` (8 cm), weighted by the standing-floor prior and approached with `anchor_vertical_tau_secs` (0.3 s). With zero weight the anchor height follows FK, so `foot_locked = true` does not guarantee a fixed vertical coordinate. That intentional vertical freedom avoids an unsupported floor-height guarantee and can permit vertical drift. These are model assumptions, not support measurements.
- **Diagnostics.** `EstimatorStatus` adds `stance_active`, `stance` (`StanceHeadingOutput`, radians; status `idle` when not stepped), `contacts`, `contact_speed_allowance_mps`, `contact_torso_allowance_mps`, `double_support`, `leg_ik_active`, `leg_ik` (including the frame's `lock_break_m` and `root_max_m`) and `support_floor` (applied `vertical_m`, `budget_m`, `support_foot`, `support_weight`, `gap_m`, `limited`, `raised`). All new fields default when reading older recordings. `EstimatorConfig.contact`, `.stance` and `.leg_ik` hold the tuning; invalid values are rejected by `validate`.
- **Replaying real recordings.** `chadfbt --replay FILE --dump OUT.jsonl [--every N] [--estimator JSON|@FILE] [--raw-dimensions]` re-solves an input-only recording with the current code (synthetic solve times from the live pacing rule, events in file order, the app's dimension normalisation unless `--raw-dimensions`) and writes decimated frames with joints, segments, targets and estimator diagnostics. Its output is model output on real motion for regression checks; it has no ground truth and is not an accuracy measurement.

Limitations, beyond those listed in the specification: firmware-held segments are never stance-filter evidence. The torso compliance budget does not cover a model error with an upright torso (for example sitting on a chair, where an earlier replayed live session left the feet above the floor). Near-horizontal thighs with vertical calves do not establish floor support: ordinary chair sitting and raised unsupported feet remain ambiguous, and a bed can support the pelvis above the floor. Seated and lying behaviour specifically:

- The thigh taper, the squat-bow rule, the backward-lean rules, the `explained` fade, the 5 mm deadband and the 1° flexion slack are independently chosen heuristics, not paper-derived or measured thresholds. Folded legs under an upright torso lose the floor prior, so genuinely grounded seated feet can float when the body model is wrong; a forward lean on a seat with the feet off the floor, or perched with the feet on a rung, is pulled down. Side-lying and prone torsos still earn bow budget and slack (their tilt is not backward); only the leg tapers protect those poses.
- Nothing models a seat or bed height, and the pelvis has no positional measurement. The torso is two rigid rods with no pelvis segment, so posterior pelvic tilt or a slouch when sitting can leave the modelled pelvis a few centimetres low in the raw chain, before any correction.
- `normalize_chain_height` absorbs any leg/torso proportion error into `chest_to_hip_m`. That is invisible standing, where only the total matters, but shifts the seated pelvis.
- Pull-down transients can still occur while sitting down or standing up, while the leg passes through the tapers.
- Evidence: synthetic exact-truth probes through `TrackingCore` with app-like jitter (chair with feet on and off the floor, recline with footrest, supine flat, supine knees-up on a raised platform, side-lying, floor sitting, cross-legged) ended within about a centimetre of the synthetic truth at hip, knee and ankle, where the committed code dropped the pelvis by tens of centimetres for supine knees-up and raised the knees of flat legs by centimetres. These probes use the estimator's own body model. A replay of one live session that contains a short seated segment (no reclined or lying data exists) showed the pre-change pull-down lowering the pelvis during sit-down, stand-up and forward-leaning crouches; with the new settings ablated the same replay differed by millimetres in upright-leg spans and by centimetres only in seated or folded-leg spans, which bounds the standing regression risk in that one session and says nothing about accuracy. Sitting on a seat of known height and lying down have not been validated on a worn body.

The synthetic tests show that the integration matches the model (common-mode leg drift removed while walking, no false correction from head-only turns or rebases, exact bone lengths, stale and held inputs ignored, determinism, nonfinite-input robustness). They do not show that the model matches a human body or say anything about performance relative to SlimeVR.

The experimental knee correction is **off by default**. It checks recent flexion excitation, moderate current flexion, conditioned projected joint axes, a 6-degree anatomical deadband, bounded residuals, fresh data and acceleration. Equal/opposite yaw changes preserve common global heading; they do not identify which sensor drifted. Its 20-degree-per-segment budget applies to its own accumulated correction per knee (reset by neutral/forward calibration and assignment changes), not to recovery offsets. With `enable_stance_heading` on it is skipped (`superseded_by_stance_filter`): the filter has its own uncertainty-weighted knee prior, and two writers of the same yaw would fight. A human knee is not a perfect hinge. The diagnostics describe why a factor was skipped. Confidence values are engineering scores, not probabilities or demonstrated accuracy estimates.

A separate `heading_shadow::RelativeHeadingEstimator` now provides a sliding-window research path. It robustly fits a constant relative yaw between calibrated joint axes and reports the exact local curvature of its frozen-weight quadratic surrogate, the scalar Gauss–Newton curvature, and the unavoidable common-yaw nullspace. Motion coverage, input confidence and residual thresholds are separately labeled engineering gates. A model-dependent candidate is not proof of drift: identical input can represent real twist. This module cannot change `TrackingCore`, mounting, recovery or live output, and does not enable or replace the existing optional correction.

Create one shadow estimator per pair and pass `HeadingPairSample` containing calibrated segment quaternions, original measured timestamps, roles, validity, confidence, provenance and calibration/continuity epochs. Undo any production world-up yaw adjustment before analysis. Firmware-held, invalid, stale, misaligned and out-of-order input cannot build a window; reused samples are never counted again. Advance epochs on calibration/reference/transport changes. `report(now)` returns serializable diagnostics and refuses to evaluate before accumulated observations. Receipt-time alignment is not sensor-clock synchronization.

The optional independent-witness interface can veto a hinge candidate without blending contradictory evidence away. The supplied joint-center acceleration helper requires synchronized actual specific force, gyro/angular acceleration, known sensor-to-joint offsets and asserted total error bounds. Current fused-quaternion telemetry does not establish that contract; the runtime must not fabricate witnesses from it. A torso contact-heading hypothesis alone also does not measure relative knee heading. Detailed equations, conditioning definitions and limitations are in [heading-shadow.md](../../docs/research/heading-shadow.md).

Run the deterministic shadow scenarios with:

```powershell
cargo run --release -p tracking-core --example heading_shadow -- --json local-data/benchmarks/heading-shadow-synthetic.json
```

This reports model residual separately from synthetic pose error, including a real-twist counterexample, common yaw, true turns, degenerate geometry, isolated outliers and asserted independent witnesses. It is not a hardware accuracy or latency benchmark. The mathematical contact-heading experiment is separately documented in [contact-heading.md](../../docs/research/contact-heading.md).

All IMU-derived joint positions are inferred. Without a direction-certified foot IMU, foot orientation uses a neutral ankle relative to the calf and lower confidence; ankle articulation is unmeasured. Optional upper-arm and foot orientations require manual direction confirmation because the six-role skiing procedure does not solve them. Controller-only elbows are uncertain IK estimates. Required stale inputs invalidate dependent targets unless the explicit firmware-held assumption above is eligible; that case remains visibly estimated with reduced confidence.

`TrackingConfig.enable_preview_motion` enables the experimental desktop-only `preview_motion` layer (core default false, app default true). It translates all joints and targets together from inferred floor/support-foot constraints, exposes translation and contact hypotheses in `TrackingFrame.preview_motion`, and never makes targets valid or changes measured segment rotations. Neutral calibration resets its local origin. Stale data, discontinuities and ambiguous motion release contact and hold displacement. It is not an absolute-position measurement or validated walking estimator; the live HMD path remains separate. There is still no optimized spine, learned residual network or raw gyro fusion.

The synthetic tests verify invariants, gates, malformed data and injected relative yaw behavior. They are not a measurement of hardware accuracy, latency, long-session drift or superiority over SlimeVR. See [the source research and evaluation plan](../../docs/research/tracking-research.md).

Run the deterministic solver benchmark with:

```powershell
cargo run --release -p tracking-core --example benchmark -- --json local-data/benchmarks/tracking-core-synthetic.json
```

The benchmark compares six and ten sensors with the experimental correction off/on, and six and ten sensors with the application's estimator defaults on (prediction, HMD extrapolation, auto rebase, stance heading filter, leg IK). Every trial starts with fresh calibration and 1,000 untimed moving frames, followed by 10,000 timed solves; three trials rotate case order. Synthetic timestamps advance at 100 Hz while execution runs unpaced. It reports p50/p95/p99/max elapsed wall time for `solve`, including output construction and excluding input generation/ingestion, output destruction, UI, networking and driver work. Timer overhead and per-trial summaries are included in JSON. This is a CPU-cost experiment, not a real-time scheduling or motion-to-photon measurement.

Paired 120-second error scenarios use the default correction rate and compare analytic projected joint headings. They include a drifting calf, true anatomical twist producing identical observations, common-mode drift, and a real global turn. Both absolute segment errors and relative knee errors are reported so reducing a constraint residual cannot be mistaken for recovering true pose. No physical data or SlimeVR comparison is included. Optional arguments are `--frames`, `--warmup`, `--trials`, and `--json`.

The [observed synthetic results](../../docs/research/synthetic-benchmark-results.md) record one release run, its environment, timing boundaries and the non-hinge counterexample. That counterexample is mathematical ground truth, not a validated biomechanical knee model.
