# SlimeVR firmware 0.7.2: stationary rotation reporting

Source inspected: official SlimeVR-Tracker-ESP tag `v0.7.2`, commit `c12c475fe067e74005e7dd83999bc3a19b478b15`. A device reporting that firmware version could still be a customized build; a version string alone does not prove its build flags or behavior.

- In [debug.h](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/src/debug.h#L81-L85), stock `OPTIMIZE_UPDATES` is a compile-time true. The comments say disabling it sends updates at the sensor update rate. In [Sensor::setFusedRotation](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/src/sensors/sensor.cpp#L39-L49), the flag suppresses a new packet while all quaternion component differences from the last one sent are less than [0.0001](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/lib/math/quat.cpp#L120-L122).
- [SoftFusion](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/src/sensors/softfusion/softfusionsensor.h#L238-L269) computes fused samples at an up-to-100-Hz target and calls both rotation and linear-acceleration setters. But [Sensor::sendData](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/src/sensors/sensor.cpp#L53-L72) sends the acceleration only inside the new-rotation branch, after the quaternion. Thus acceleration does **not** independently certify an unchanged quaternion. If acceleration appears fresh while rotation does not, investigate actual bytes, loss/reordering, parsing, and firmware customization.
- The documented [feature flags](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/src/network/featureflags.h#L34-L40) negotiate bundling; the available [sensor toggles](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/src/sensors/SensorToggles.h#L32-L36) cover magnetometer and calibration settings. No runtime network setting to disable this compile-time optimization was found. Rebuilding and flashing a matching firmware configuration is a possible intervention, but must be separately evaluated against exact hardware and user authorization; it has not been done.
- Sensor status is transmitted on change/unacknowledged state, [not a periodic fresh proof once acknowledged](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/src/network/connection.cpp#L504-L535). Its soft-fusion watchdog allows [two seconds](https://github.com/SlimeVR/SlimeVR-Tracker-ESP/blob/c12c475fe067e74005e7dd83999bc3a19b478b15/src/sensors/softfusion/softfusionsensor.h#L182-L198) without a fusion update before an error; this is not suitable as proof of an up-to-date orientation.
- In [SlimeVR Server's packet parser](https://github.com/SlimeVR/SlimeVR-Server/blob/83941fd38e91cc91ca6b360deab5c2ae986dd1b6/server/core/src/main/java/dev/slimevr/tracking/trackers/udp/UDPProtocolParser.kt#L10-L22), any accepted packet refreshes tracker heartbeat; [its tracker](https://github.com/SlimeVR/SlimeVR-Server/blob/83941fd38e91cc91ca6b360deab5c2ae986dd1b6/server/core/src/main/java/dev/slimevr/tracking/trackers/Tracker.kt#L310-L327) distinguishes rotation data ticks from heartbeat timeout. This is an upstream liveness policy, not a guarantee that the specific sensor's current orientation is observed.

A long gap between rotation updates while a tracker is still is compatible with change suppression, but its absence over UDP cannot distinguish suppression from a lost latest update or a stalled sensor until further evidence arrives. Even a contiguous packet sequence proves only the history up to the last received packet; it cannot establish whether the next movement packet was lost before a later numbered packet reveals a gap. The current app therefore does not refresh quaternion age from arbitrary heartbeat or acceleration. Diagnostic capture can distinguish packet classes, sequence gaps, and actual accelerations from old cached values; hardware exercise and capture are required before revising the policy.

## Experimental compatibility mode

The implementation can retain a last measured quaternion as **estimated firmware-held** evidence, with its original receive time unchanged and confidence capped at 0.45. Eligibility requires a MAC-identified device reporting exactly firmware `0.7.2`, a single reported sensor (ID 0), a previously reported healthy sensor status, recent accepted device traffic, a previously measured quaternion, and an uninterrupted accepted sequence since the eligibility epoch. Missing, duplicate, out-of-order, malformed, or unknown data, explicit sensor errors, worker pauses, endpoint/session changes, or traffic timeout revoke the assumption until a new quaternion arrives. The displayed raw rotation age remains the time since a real quaternion. Fresh measured rotation remains available for other firmware and multi-sensor devices.

This is a **compatibility assumption**, not proof that a stationary sensor remained healthy or that no most-recent UDP packet was lost. The last status may be old, packet loss is discoverable only when a later sequence arrives, and the firmware version can be used by modified builds. It must be visibly labeled and cannot support a measurement-accuracy claim. An interrupted or motionless sensor can look unchanged while the tracker continues sending unrelated traffic. Validate this failure mode and behavior on the actual hardware before relying on live output.
