# ChadFBT SteamVR driver prototype

The server driver has eight generic tracker slots but adds a slot's device to SteamVR only after the application first sends a valid pose for it, so slots the app cannot drive (for example elbows without upper-arm sensors) never appear; the anchor helper reads the headset and controller poses in SteamVR standing space. No pose is valid until the application sends calibrated, fresh estimates. A registered tracker that later loses its pose stays at its last valid position, reported out of range, and disconnects when the app has been silent for more than 1 s (see [protocol](PROTOCOL.md)). Slots do not imply physically measured foot tracking. See [protocol](PROTOCOL.md) and [research](../docs/research/steamvr-integration.md).

Install Visual Studio 2022 C++ x64 tools and a Windows SDK, then run `powershell -ExecutionPolicy Bypass -File driver/build.ps1`. Alternatively use `cmake -S driver -B driver/build-cmake -A x64` then `cmake --build driver/build-cmake --config Release`; the build copies `openvr_api.dll` beside the helper. The driver folder must remain named `chadfbt`, matching its manifest and DLL.

While SteamVR is stopped, run `powershell -ExecutionPolicy Bypass -File driver/registration.ps1 -Action install` (pass `-VrPathReg` for a nondefault SteamVR installation). Use `-Action status` and `-Action uninstall` for discovery and removal. Registration writes to OpenVR configuration and may hot-plug when SteamVR is running. Restart SteamVR when convenient and check that the add-on is enabled; SteamVR may require its `steamvr.activateMultipleDrivers` setting for an additional driver. The script does not alter that setting or automatically assign tracker roles. Assign roles in SteamVR's Manage Trackers UI. Disable or disconnect other tracking drivers when their active trackers duplicate the same body roles; this system already has other external drivers registered.

Start SteamVR and the main application; the app launches the companion helper when available. The helper checks that SteamVR is already running before initializing OpenVR, and the app retries after startup or a disconnect. For standalone diagnostics, run `driver/build/chadfbt-anchors.exe`. It does not request or emulate skeletal hand data. Confirm current hand behavior in the target game separately.

With SteamVR already running, `driver/build/chadfbt-anchors.exe --inspect` prints one JSON snapshot of standing-space HMD height and the eight ChadFBT tracker slots. It does not send tracker or anchor packets. A slot that has not yet received a valid pose in this SteamVR session reports `"present": false`. Invalid or disconnected poses have null positions or height. A slot name comes from the driver's serial number and does not prove SteamVR has assigned that tracker role. The command will not start SteamVR; it exits with an error if OpenVR initialization fails.

To explicitly assign ChadFBT's six core output roles while SteamVR is running, run `driver/build/chadfbt-anchors.exe --assign-core-roles`. This writes only `/devices/chadfbt/chadfbt_hip`, `chest`, `left_foot`, `right_foot`, `left_knee`, and `right_knee` in SteamVR's `trackers` section, mapping them to Waist, Chest, LeftFoot, RightFoot, LeftKnee, and RightKnee. It uses OpenVR's settings API and reads back every requested value. It leaves elbow slots and every other device's assignments intact. The command reports each result and exits nonzero on any write error, read error, or mismatch. Writes are independent: a partial failure can leave successful changes applied. It does not publish poses or establish VRChat calibration. Roles are stored by device path, so they can be written before a slot's device has been added; SteamVR's Manage Trackers UI lists a tracker only after its first valid pose. The ordinary helper and `--inspect` never assign roles. The API and key format are documented by [Valve's tracker-role documentation](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/docs/Driver_API_Documentation.md#trackers-full-body-tracking).

SteamVR logs from 2026-11-14 show this driver loading and all eight tracker devices being added alongside Steam Link (the driver then added every slot at `Init`; it now adds slots lazily, which has not yet been observed live). SteamVR did not assign their roles automatically; assign them manually. Those logs do not establish that the devices produce correct poses or that VRChat recognizes their assigned roles. Validate the standing-to-driver tracking-space transform, each assigned role, stale behavior, and recalibration/recenter behavior before relying on the output. Uninstalling removes only this registered external path; existing settings and roles are not changed.





Each tracker reports `Prop_ControllerType_String` `chadfbt_tracker`, the input profile `{chadfbt}/input/chadfbt_tracker_profile.json` (`chadfbt/resources/input/`, a single `/pose/raw` generic-tracker profile modelled on SteamVR's own `vive_tracker_profile.json`), and the render model `{htc}/rendermodels/vr_tracker_vive_1_0`. Whether SteamVR loads that profile and model without errors has not been checked in a live session. SteamVR logs `[Input] <app> (chadfbt_tracker) has no configured binding. Input will not be available` for apps with an action manifest, such as `steam.client` and VRChat. Bindings are per application: Valve's documentation makes driver `default_bindings` optional and keyed by app, and a binding file maps that app's actions, which these trackers do not provide (they expose only `/pose/raw`, no buttons). SteamVR's own `vive_tracker_profile.json` and SlimeVR's tracker profile also declare no `steam.client` bindings, VRChat's bundled bindings cover no body-role tracker types, and the same log on this machine also reports the message for `oculus_touch` and `rift`. It concerns action input, not device poses, and is expected to be harmless. Role assignment does not depend on the profile: Valve documents the Manage Trackers UI for every `TrackedDeviceClass_GenericTracker`. The optional `tracker_types` key (used by Valve and SlimeVR) only switches the controller type per role and is not declared here. Poses are submitted from a driver-owned receive thread as soon as each frame arrives; see [protocol](PROTOCOL.md) for velocity, prediction-offset and out-of-range semantics.

Both `build.ps1` (cl's default `/MT`, with `/O2`) and the CMake build (`CMAKE_MSVC_RUNTIME_LIBRARY` MultiThreaded) link the static C runtime. The Windows x64 driver built by `build.ps1` on 2026-11-15 imports only `KERNEL32.dll` and `WS2_32.dll`; the helper also imports `WINMM.dll` (for the `timeBeginPeriod` fallback timer). The bundled OpenVR client imports `KERNEL32.dll` and `SHELL32.dll`. This was checked with MSVC `dumpbin /dependents` on these artifacts, not established as a guarantee for future rebuilds. The helper loads `openvr_api.dll` dynamically, and a working installed SteamVR runtime is still required. Static import inspection does not verify dynamically loaded runtime or graphics components on other machines.
